## 一、20 首抽样脚本早期按歌名取第一个结果而命中翻唱的缺陷说明

### 1. 现状与修复区分
- **早期脚本缺陷**：在早期提交的 `scripts/test-20-sample-songs.mjs` 中，搜索请求仅拼接了 `q = song.name`，且直接提取返回结果的第一个条目（`tracks[0]`），未对歌手名进行严格相似度比对。
- **影响的曲目**：
  - 《晴天》命中了《晴天(深情版) - Lucky小爱》（非 VIP 完整流，11.1MB）；
  - 《稻香》命中了《稻香(深情版) - Lucky小爱》（非 VIP 完整流，9.26MB）。
- **处置现状**：
  - 在全量实测采集脚本 `scripts/measure-20-sample-songs-raw.mjs` 中，**已修复**该缺陷，加入了 `title` 与 `artist` 的归一化过滤；
  - 但在作为历史对照基准的 `scripts/test-20-sample-songs.mjs` 中，仍保留了原有逻辑以供比对历史测试结果。若后续需彻底统一度量衡，应将历史脚本的查询参数也替换为严苛模式。

## 二、试听相对阈值公式对极低码率完整流的边界风险

### 1. 相对阈值公式现状
当前网关采用动态相对阈值公式：
$$\text{effBitrateKbps} = \max(96, \text{nominalBitrateKbps} \times 0.55)$$
$$\text{baselineBytes} = \text{expectedDurationSec} \times \frac{\text{effBitrateKbps} \times 1000}{8}$$
$$\text{ratio} = \frac{\text{totalBytes}}{\text{baselineBytes}}$$

### 2. 覆盖与未覆盖场景
- **已修复与已验证场景**：
  - 320kbps 标称码率下，45 秒试听切片（1.8MB）在 240 秒与 150 秒曲目下 ratio 分别为 0.34 和 0.55，均被精准识别为 `trial`（通过 Test 12 单元测试验证）；
  - 128kbps 标称码率下，4 分钟真实完整音频（3.84MB）ratio 为 1.33，精准识别为 `full`。
- **潜在误判风险（极低码率完整流）**：
  - 像酷狗平台下发的某些低质完整流（例如《红日》，实际物理码率仅为 **48 kbps**，总文件大小仅约 1.6MB）。
  - 若客户端请求时传入了标称 128k 或 320k，该音频的总字节数（1.6MB）低于公式推导出的基准字节数（例如 128k 基准为 2.88MB），此时 `ratio` 仅约为 0.55，将被网关判定为 `trial`。
  - **技术定性**：这属于“防御性误判”——虽然曲目时长是完整的，但其音质严重低于请求预期的标称码率。系统宁愿将其标记为试听并尝试寻找其他音源的高清完整流，也不愿将 48k 劣质音频冒充 320k 高清完整流交付给用户。
  - **未来优化方向**：在边缘引入 HTTP Range 获取音频头部 metadata 解析出的真实 duration 与预期 duration 比对（$\Delta t \le 6\text{s}$），将“时长完整性”与“码率质量”解耦为两个独立维度输出。

## 四、酷狗等低码率完整流的音质展示问题

- **问题现象**：前端播放器界面的音质切换器（如 Standard / High / Lossless）目前仅反映了当前歌曲请求的查询参数与上游返回的标称档位。
- **技术局限**：在上游部分源（如酷狗 free-match、酷我）返回降级音频时，即便网关成功获取到了完整音频流，其实际物理码率可能被上游悄悄降至 48kbps ~ 96kbps。此时前端界面依然显示 128k 或 320k 徽标，导致用户视觉感知与实际听觉体验存在偏差。
- **计划改进**：后续可在播放器加载音频后，使用 `music-metadata-browser` 在客户端本地解码第一帧音频头，提取真实的 `bitrate` 并动态覆盖播放界面的展示。

## 五、交付报告中仍未经实测、只属推断的内容诚实说明

1. **注入个人合法 VIP Cookie 后的取流表现**：
   - 报告中提到的“注入 VIP Cookie 后付费曲目可出 320k 完整流”系基于逆向协议标准规范的理论推断。由于本项目恪守开源合规与非商业准则，在生产和测试环境中从未集成或硬编码任何个人真实 VIP Cookie，故未在真实线上环境中进行带有个人凭据的流提取测试。
2. **极端网络丢包下的单次重试收益模型**：
   - 取流链路重试方案（`maxRetries=1, timeout=2200ms`）目前仅作为架构优化建议提出，代码中仍维持零重试以防止放大上游压力。该方案的延迟改善与成功率数据属于理论分析，尚未经过大规模线上流量验证。

## 六、上线时 Pages 与 VPS 引擎版本协同部署注意事项

1. **同构契约依赖**：
   - Functions 边缘网关与 VPS 上的 `sonic-engine` 必须协同发布。若只更新 Pages 边缘代码而不更新 VPS 容器，会导致新增的 `X-Sonic-Stream-Type` 标头、跨源探测参数无法在引擎侧正确识别。
2. **部署顺序建议**：
   - 第一步：先在 VPS 上构建并重启本地引擎容器（`docker compose build engine && docker compose up -d`），确认健康端点返回 `200`；
   - 第二步：部署 Cloudflare Pages 前端与 Functions 网关（`npx wrangler pages deploy dist`）。
